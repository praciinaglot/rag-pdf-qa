# Ask Your PDF: a RAG app with measured retrieval and answer quality

   **Live demo:** https://rag-pdf-app-mxotstw2cvykgwedumavv6.streamlit.app
   
A question-answering app over PDF documents. It finds the most relevant passages, then has an LLM answer using only those passages, with page citations. If the answer isn't in the document, it says so instead of guessing.

The focus of this project is **evaluation**: I measured retrieval and answer quality, tested design choices against each other, and recorded what did and did not work.

## How it works

1. **Ingest:** PyMuPDF reads the PDF page by page and cuts the text into 400-character chunks (50 overlap), keeping the page number for each chunk.
2. **Retrieve:** chunks and questions are embedded with `BAAI/bge-small-en-v1.5`, and the top 6 chunks by cosine similarity are selected.
3. **Answer:** Gemini answers using only those chunks, cites page numbers, and replies "I couldn't find this in the document" when the context does not contain the answer. Requests retry automatically and fall back across several Gemini models when one is busy.
4. **UI:** a Streamlit app with PDF upload, chat, and a Sources panel.

**Stack:** Python, PyMuPDF, sentence-transformers, NumPy, Google Gemini API, Streamlit.

## Evaluation setup

- Test document: a 200+ page machine learning textbook.
- 25 questions were generated by an LLM from random passages, each labeled with its source page. I removed 5 that were vague or irrelevant, judging only the question quality and not whether the bot missed them, which left **20 questions**.
- **Hit@k:** is the source page among the pages of the top k retrieved chunks?
- **Answer quality:** Gemini graded each answer as CORRECT, INCORRECT or NOT_FOUND against the full source page.
- **Trap questions:** 5 unanswerable questions (cricket, recipes, etc.) check that the bot refuses instead of hallucinating.

## Results

### 1. Chunk size matters (retrieval)

| Chunk size / overlap | Chunks | Hit@1 | Hit@4 |
|---|---|---|---|
| 200 / 25 | 2519 | 70% | 80% |
| 300 / 40 | 1729 | 70% | 85% |
| **400 / 50 (chosen)** | 1307 | **85%** | **90%** |
| 500 / 60 | 1062 | 85% | 85% |
| 800 / 100 (baseline) | 704 | 70% | 90% |
| 1200 / 150 | 502 | 75% | 80% |
| 1600 / 200 | 414 | 60% | 70% |

Moving from the 800-character baseline to 400 raised Hit@1 from 70% to 85% with Hit@4 unchanged at 90%.

### 2. Answer quality (400/50 chunks, top 6 chunks)

| Metric | Result |
|---|---|
| Correct answers | 17 / 20 (85%) |
| Incorrect answers | 0 |
| "Not found" (safe failure) | 3 |
| Source page retrieved | 18 / 20 |
| Unanswerable trap questions refused | 5 / 5 |

The bot never gave a wrong answer on this set. All 3 misses were "I couldn't find this", which is the safer way to fail.

### 3. What did not work

- A word-boundary chunker (never splitting words) left Hit@1 unchanged at 70% and lowered Hit@4 from 90% to 80%.
- Chunks smaller than 400 characters lost context and did worse.

## Limitations

- Only 20 questions, so each is worth 5 points and differences of 1-3 questions are within noise.
- The questions were generated from 800-character chunks, which may slightly favor that size (400 still won).
- Gemini graded Gemini's answers, which can make scores a little generous.
- Hit@k is a strict page-level metric: one answer was graded correct even though the exact source page was not retrieved.
- 2 of the 3 "not found" answers had the right page retrieved, so the small chunks missed the exact sentence. Adding neighboring chunks is the next experiment.
- Tested on one textbook only. Scanned PDFs, tables and figures are not handled.
